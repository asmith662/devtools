## Question and interpretation

Can exact declaration grounding and explicitly selected OWNER_RESOURCE,
MIRRORED_RESOURCE and REFERENCING_RESOURCE relations retain useful independently
adjudicated witness coverage and complementary structure with a materially smaller
task-relative candidate surface than lexical localization? No favorable answer is
assumed.

The exact development task is retained verbatim in `treatment.json` and `TASK` in
[treatment.py](treatment.py). That identical text is the sole global lexical query.
Purpose, task, query and obligation remain different concepts. Nine shared anchors
support eleven mandatory obligations, all applicable to the stated task:

1. Native source declaration identity.
2. Import/member bindings and direct facade re-exports.
3. Explicit module interpretation and immediate package membership.
4. Static public exposure and explicit `__all__` boundaries.
5. Unsupported/dynamic behavior, ambiguity and abstention.
6. Repository/snapshot identity, dependencies and provenance.
7. Exact Reference integration boundaries and consumers.
8. Public package/API conventions and ownership.
9. Native RI test patterns and regressions.
10. Authoritative documentation impact.
11. Protected development validation policy.

Each has a named criterion, task provenance, shared-anchor bindings and one exact
caller query with positive soft roles. No conditional applicability was invented:
the task explicitly requires all eleven concerns. All pre-execution accepted
witness alternatives are empty. Blind adjudication may identify interpretation
gaps or revise applicability independently; the treatment remains frozen.

## Grounding and candidate shapes

Nine request identities name eight exact source declarations and one Python
package module. Exact source selection may ground decorated declarations without
establishing binding identity. No locator was resolved or prechecked against
declaration matches. `exposure`, `abstention` and `verification` intentionally have
no exact grounding: current locators cannot identify those abstract/new task
concepts. An obligation may still use a separately justified shared anchor.

Each serialized recipe identifies its obligation, caller identity, member keys,
grounding request, operator, reason and task provenance. Fixed recipes retain
caller hypothesis identity; branching recipes retain caller family identity.
Specs are not instantiated production grounded recipes. OWNER projects a plausible
native contract owner. MIRROR is used only for the test obligation and proposes
exact convention counterparts, without claiming that they validate the source.

Reference-only families propose one exact referencer. Owner-plus-Reference families
propose an owner contract plus **one** consumer as complementary candidate members;
the children compete unresolved. Package-plus-module-consumer proposes an explicit
public package surface plus one module API consumer. Each family has at most one
branch. No recipe combines all referencers or creates a Cartesian product.

Explicit exposure, documentation and validation have no structural recipe: none
of the allowed relations establishes new public exposure, documentation authority
or validation-policy connectivity. Their lexical lanes remain present. No recipe
is added simply to make every obligation structurally covered.

All Reference branches use a shared `max_results = 16`, a prospective human-review
budget. The shared work limit is **4096 distinct supplied source analyses authorized
for native replay/enumeration**. This broad finite budget permits complete scan of
the archived ordinary Python frame; its fit is checked without querying any seed's
References. It is not a byte, occurrence, time or total integrity-validation bound.
No bound was selected from target fanout, gold, or useful historical candidates.
Complete result overflow admits zero children with an exact count; incomplete work
admits zero children, unknown total and deterministic uncovered frontier. There is
no first-K, ranking or pruning. Same-owner References remain eligible; fixed-owner
collisions are explicit branch failures, never prefiltered or repaired.

## Stage order and durable execution protocol

1. **Stage A (this checkpoint):** freeze inputs/settings/metrics, validate, commit.
2. **Stage B (future):** verify the exact committed Stage A artifacts and frozen
   implementation/runtime compatibility. Load only verified archived inputs.
   Execute one production lexical acquisition (one global plus eleven obligation
   BM25 lanes), and one production routing operation. Resolve each of the nine
   distinct grounding requests exactly once and retain an identity-keyed cache.
   Bind all recipe specs to those captured results, including unresolved outcomes;
   instantiate the corresponding fixed or branching identities/members and one
   combined production plan with archived Reference inputs and captured supports.
   Execute one generation invocation. Do not re-resolve initial groundings per recipe.
   Production generation/association **integrity replays** of grounding, mirror and
   Reference evidence are architecture-required validations; retain/account for
   them separately from the nine initial grounding executions. They must replay
   archived content, never acquire current files. Do not monkeypatch validators or
   silently promise that the existing API performs no integrity replay.
   Persist each native result durably immediately after the operation returns,
   before correspondence checking, JSON serialization or analysis. Use exclusive
   captures with digest/identity receipts and operation-level completion markers.
   A validator failure must resume post-processing from native captures, never
   reexecute a completed operation. Refuse output overwrites. Only after native
   durability validate correspondence and construct canonical Stage B artifacts;
   commit them. The execution harness is deliberately not implemented in Stage A.
3. **Stage B.5:** create a treatment-free blind packet and commit it.
4. **Stage C:** a fresh session independently adjudicates the blind packet and
   freezes/commits judgments.
5. **Stage D:** join captured treatment with frozen blind gold and analyze.

## Blind protocol and interpretation

Stage B.5 includes only exact task, purpose, anchors, obligations/criteria, frozen
resource identities/contents and neutral adjudication instructions. It excludes
queries, roles, all grounding requests/locators/results, recipes/operators, branch
configuration, Reference bounds, generated hypotheses/targets and operator provenance.
Stage C independently judges applicability, REQUIRED, HELPFUL_ONLY, UNNECESSARY,
unresolved, acceptable alternatives, complementarity, competition, task-start
inferability, inherent discovery and interpretation gaps. Gold must not know whether
the Reference treatment worked.

No arbitrary pass/fail threshold is frozen. Encouraging evidence means unique
REQUIRED gain beyond OWNER/MIRROR, better complete-witness coverage, a substantially
smaller surface than lexical completion prefixes and manageable unnecessary
expansion/fanout/abstention. Poor evidence means duplicate structural reach, many
unnecessary referencers, little complete-obligation gain, frequent abstention or a
surface approaching lexical review size. Report observations without a forced verdict.
No learned ranking, embeddings, PPR, RRF, scores, automatic recipes, recursive
traversal, runtime invocation, public exposure inference or witness resolution is
tested by structural generation.
